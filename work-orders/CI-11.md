# CI-11 — Publish the image in the deploy workflow, so the pull has something to pull

Status: planned · Tier: 2, prod-infra · Target repo: workflow-templates (main) + the four consuming app repos · Datum: 2026-08-08 · Completes CI-9/CI-10

## A. Envelope (Expertenchat — authoritative WHAT/WHY)

### Goal

Make the pull-based deploy actually work by publishing the image **in the same job that deploys it**,
immediately before the pull. CI-9 and CI-10 built a correct pull path on top of an assumption that
does not hold in this estate: that CI runs before a deploy.

### Why — the trigger topology, verified

```
ci.yml     on: pull_request: [develop, main]  +  workflow_dispatch     ← no push trigger
main.yml   on: push: branches: ['develop', 'main']                     ← the deploy
```

The two workflows react to **disjoint events**. A push to `develop` fires only the deploy, never CI.
And this estate commits **directly to `develop`** by `AGENTS.md` policy — no feature branches — so
that is the normal path, not an edge case. CI runs only on the `develop → main` promotion PR.

Consequence, observed live 2026-08-08 across cockpit, hram, jg-ferien and survey_app: the GHCR login
succeeds (CI-10's auth fix is correct) and `docker compose pull` then finds no image for the SHA,
because nothing ever published one. All four staging deploys failed identically and **harmlessly** —
every container kept running on its previously-built image, no outage, no rollback needed.

Both CI-9's and CI-10's reviews missed this because both examined the workflow files in isolation and
never checked which events actually reach them.

### The fix is smaller than the diagnosis suggests

`main.yml`'s deploy job already runs `runs-on: [self-hosted, netcup]` — the **same runner** that
builds in CI, with the same warm BuildKit cache and the daily 20 GB prune. It already declares
`permissions: packages: write` and already passes `github_token: ${{ secrets.GITHUB_TOKEN }}`.

So this needs **a step, not a job**: build-and-publish between the existing checkout and the
`deploy-app` action. Same job, same runner, same checkout — sequencing is guaranteed by step order,
with no `needs:`, no `workflow_run`, and no cross-workflow race. The job's existing
`concurrency` group (`cancel-in-progress: false`) covers it automatically, so two pushes queue
instead of racing.

### Scope

1. **Extract the publish logic from `app-ci.yml:175-213` into a composite action** so both callers
   share one implementation. Two copies of this logic is the divergence class GC-6 exists to guard
   against; do not create it here.
2. **`main.yml` gains the publish step** before `deploy-app`, in the same job.
3. **Resolve the SHA once, after checkout, and use it for both publish and deploy.** This is a real
   defect in the current step, not a cosmetic point: `main.yml`'s `workflow_dispatch` path
   explicitly checks out a *different* ref (`staging → develop`, `production → main`), while
   CI-10's publish step tags with `github.sha` — the SHA of the *triggering* ref. On a dispatch
   those diverge, and you would build one commit and deploy under another commit's tag. Green,
   silent, wrong. Take the SHA from the working tree after checkout.
4. **Roll the step into the four repos** whose pins are already on the new templates: cockpit, hram,
   jg-ferien, survey_app. Their deploys are currently red on every push; this is what turns them
   green.

### Non-goals / do-not-touch

- **NOT test-gating staging deploys.** This is the decision this WO must not make by accident.
  Today a push to `develop` deploys immediately and untested — staging *is* the test bed, and that
  is a deliberate property of this estate, not an oversight. Publishing an image is a **deploy
  prerequisite**; running the test suite is a **quality gate**. Coupling them is the reason option
  "deploy calls `app-ci.yml`" was rejected: it would silently make an unrelated test failure block a
  staging fix. If test-gating staging is ever wanted, it is its own WO with its own operator
  decision.
- **NOT** adding a `push` trigger to `ci.yml`. It would not sequence anything — two independently
  triggered workflows can still race — and it would drag the test suite onto every push, i.e. the
  non-goal above through the back door.
- **NOT** CI-9's transport design or CI-10's credential decision. Both stand; this only supplies the
  missing producer.
- **NOT** the remaining app repos. Only the four already pinned to the new templates are in scope —
  the rest are unaffected because their pins predate CI-9.
- Not auth/permission logic in the applications, schema, or app behaviour.

### Acceptance

- A direct push to `develop` in cockpit publishes an image and then deploys it, in one job, green.
- The deployed digest matches the image built from the **checked-out** commit — verify on a
  `workflow_dispatch` run, where the triggering and checked-out refs differ. A push-triggered run
  alone does not exercise this.
- The deploy log shows a pull and **no build step on the target host**.
- `app-ci.yml` still publishes on its own path (PRs), through the shared action, with no behaviour
  change.
- No test job gates the deploy.

### Required tests to WRITE (narrow)

- Structural: `main.yml`'s publish step precedes the `deploy-app` step in the same job.
- Structural: neither the publish action nor the deploy path references `github.sha` directly for
  the image tag — the SHA comes from the checkout. Assert the **absence** of `github.sha` as a tag
  source; that is the defect in scope item 3 and it would otherwise reappear on the next edit.
- Structural: the deploy workflow does not depend on a job that runs tests (the non-goal, pinned as
  an assertion so a later refactor trips over it).
- The shared action is referenced by both `app-ci.yml` and the deploy workflow — one implementation,
  two callers.

Scoped to the existing `.github/scripts/` structural tests. Not an estate render.

### Risks

- **The runner now builds the full production image on every develop push.** For CI-6 repos
  `app-ci.yml` builds only the lean `backend_test` target today, so this is genuinely new load on
  the runner — but it *replaces* the build that used to run on the shared prod box, which is the
  entire point of CI-9. Watch the runner's disk after the first few runs; INF-11 gave it a daily
  20 GB reclaim, and this is the first change that leans on it.
- Four repos are currently red on every push. Until their `main.yml` carries the step they stay red,
  so land the shared half and cockpit together, prove it, then the other three.
- A publish failure now blocks the deploy — correctly. That is a louder failure mode than today's
  server-side build, and it should stay loud: do not add a "publish failed, deploy anyway" path,
  which would deploy a stale image while looking green.
- The `--build` fallback from CI-9 remains the escape hatch for a registry outage. Do not remove it
  while adding a producer in front of it.

- A consuming repo's `.github/workflows/main.yml` — the deploy job: `runs-on: [self-hosted, netcup]`,

- `.github/actions/deploy-app/action.yml` — the pull side, its `IMAGE_TAG` handling and the

- `work-orders/CI-9.md` (transport), `CI-10.md` (credential) — what this completes.

## B. Implementation map (Orchestrator)

Two repos this pass: `workflow-templates` (shared half, cwd for Codex) and `cockpit` (the one
permitted rollout target). Do NOT `git add`/`commit`/`push` in either.

### 1. New composite action: `workflow-templates/.github/actions/publish-backend-image/action.yml`

Extract the body of `app-ci.yml`'s current "Publish backend image to GHCR" step (`:175-213`) into
this action almost verbatim — the logic itself (image-name resolution from `project.yaml`, the
target/no-target build branch, GHCR login, push) is correct and stays; only the interface changes
from env-vars-in-a-workflow-step to declared composite-action `inputs:`.

Inputs (mirror the current `env:` block at `:180-187`, plus one new one):
- `image_tag` (required) — the caller resolves this from the checked-out commit, NOT `github.sha`
  inline in the calling YAML (scope item 3 — this is the whole point of the WO).
- `github_token` (required)
- `backend_dockerfile` (default `'backend/Dockerfile'`)
- `backend_build_context` (default `'.'`)
- `backend_target` (default `''`)
- `hram_engine_read_token` (default `''`)
- `vite_app_mui_license_key` (default `''`)
- `existing_image` (default `''`) — **new**, not present in the current inline step. When set AND
  `backend_target` is empty, `docker tag` this image instead of rebuilding (app-ci.yml's current
  `else: docker tag "$CI_IMAGE" ...` branch, `:208-210`). `main.yml` never sets this — it has no
  earlier `$CI_IMAGE` build to reuse, so it always takes the build branch. This is what makes one
  action correctly serve both callers' different starting states.

Output: `image` — the full `repo:tag` reference actually pushed, via `$GITHUB_OUTPUT` (composite
action outputs, not the current step's `$GITHUB_ENV` — that mechanism was a same-job-only workaround
for a step following a step; a composite action's own output is the correct interface). Both
callers need this afterward: `app-ci.yml`'s "Remove CI image" step (`:215-221`) currently reads
`$PUBLISHED_IMAGE_TAG` from env — switch it to the action's `steps.<id>.outputs.image`.

Keep every existing guard: the `IMAGE_TAG`/`GITHUB_TOKEN` empty-checks (`:190-191`), the
`ghcr.io/*/*-backend` shape check on the resolved image name (`:194-197`), the OCI source label
(`:204`), login-via-stdin (`:212`). None of this logic is wrong — only its packaging.

### 2. `app-ci.yml`: switch to the shared action, resolve the tag from checkout

- After the existing checkout (`:112`), add a step resolving the checked-out SHA (e.g.
  `id: resolve_sha`, `run: echo "sha=$(git rev-parse HEAD)" >> "$GITHUB_OUTPUT"`) — even though
  `app-ci.yml` has no ref-override defect today (unlike `main.yml`'s `workflow_dispatch` path), the
  WO's own required test asserts NO caller references `github.sha` directly as a tag source
  anywhere, so both callers resolve identically. Reference `${{ steps.resolve_sha.outputs.sha }}`
  wherever `${{ github.sha }}` was used for the image tag.
- Replace the inline "Publish backend image to GHCR" step (`:175-213`) with
  `uses: ./.github/actions/publish-backend-image` (relative path — same repo), passing the same
  values that used to be read from `secrets`/`inputs` directly into the action's `with:` block, plus
  `existing_image: ${{ env.CI_IMAGE }}` **only** when `inputs.backend-target` is empty (the branch
  this preserves) — `${{ inputs.backend-target == '' && env.CI_IMAGE || '' }}` or an equivalent
  conditional expression.
- Update "Remove CI image" (`:215-221`) to reference the new step's `outputs.image`.

### 3. `deploy-app/action.yml`: accept the tag as an input instead of computing it

Both `IMAGE_TAG: ${{ github.sha }}` occurrences (`:376`, `:520`) are the scope-item-3 defect: on a
`workflow_dispatch` run, `main.yml`'s checkout step explicitly overrides the ref
(`staging→develop`, `production→main`), but `github.sha` stays the SHA of the *triggering* ref —
they can diverge. Add a new required input `image_tag` to the action's `inputs:` block; replace
both `IMAGE_TAG: ${{ github.sha }}` lines with `IMAGE_TAG: ${{ inputs.image_tag }}`. Every existing
guard downstream of `IMAGE_TAG` (the empty-checks at `:380`, `:525`, `:584`, the `.env` append at
`:402`) stays exactly as-is — only where the value originates changes.

### 4. `cockpit/.github/workflows/main.yml`: the publish step, in the deploy job

- After the existing checkout step (which already carries the `workflow_dispatch` ref override —
  this is the exact step whose output must feed the tag), add the same `resolve_sha` step as
  app-ci.yml, reading the just-checked-out `HEAD` (`git rev-parse HEAD`), so it reflects whichever
  ref the checkout step actually put on disk.
- Add a new step calling
  `uses: bigler-webapps/workflow-templates/.github/actions/publish-backend-image@<new-tag>` (the
  Orchestrator cuts this tag after the shared half lands — do not hardcode a guess; use whatever
  tag review/commit produces, and note it plainly in your summary) between the checkout and the
  existing `deploy-app` step (`:42` currently) — same job, so step order alone guarantees the image
  exists before the pull. Pass `image_tag: ${{ steps.resolve_sha.outputs.sha }}`,
  `github_token: ${{ secrets.GITHUB_TOKEN }}`, and cockpit's own Dockerfile/context values from its
  `project.yaml`/existing CI-9 wiring if it has non-default values (check — most repos use the
  defaults).
- Update the `deploy-app` step's `with:` block to add `image_tag: ${{ steps.resolve_sha.outputs.sha }}`
  (the new required input from item 3) — this MUST be the same value the publish step just used, not
  a second independent resolution.

## ADDENDUM 2026-08-09 (Expertenchat) — the registry login leaks into shared credential stores

The live verification was blocked by `docker build` failing to pull the **public** image
`ghcr.io/astral-sh/uv:latest` with `failed to fetch oauth token: denied: denied`. It was initially
read as an external, possibly transient GHCR problem, and as *not* a CI-11 regression because the
same failure appeared on the old, unchanged `deploy-app@v2.4.4` path.

It was neither external nor transient, and the old-path failure is the clue rather than the alibi.

### Mechanism, diagnosed and confirmed

A public GHCR image needs no authentication. `failed to fetch oauth token: denied` means the daemon
**did** present a credential and the token exchange rejected it for that scope. The credential is
the repo-scoped `GITHUB_TOKEN` that CI-10/CI-11 introduced, left behind in a **shared** credential
store:

- **Runner side** — `publish-backend-image/action.yml:79` logs in and never logs out. The three
  `gh-runner@1..3` slots are ephemeral but share one home, `/opt/gh-runner`. Confirmed: that
  config.json listed `auths: ['ghcr.io']`.
- **Server side** — `deploy-app/action.yml:595` logs in **inside the SSH block**, i.e. on the target
  host, and never logs out. Any subsequent server-side build on that box then presents the same
  narrow token when pulling from another namespace.

Both explain the old-path failure: the old path never logs in — it **inherits** what a new-path run
left behind.

### The blast radius was wider than the four migrated repos

`fitness-monitor` was never part of the migration and still builds on the server. It failed anyway,
because it shares a host with apps whose new-path deploy had logged in there. **On any box that had
seen a new-path deploy, server-side builds were broken for every app on it** — not only for the four
repos this WO touches.

### Resolution (operator, 2026-08-09)

`docker logout ghcr.io` as the owning user: on the runner (`gh-runner`), on **staging**, and
preventively on **contact-prod** and **innoservice-prod**. **main-prod carried no entry.**
fitness-monitor's deploy went green immediately afterwards, closing the diagnosis end to end.

### Added scope — CI-11 is not done until this lands

**Scope 5. Scope the registry credential to the job/session, on BOTH sides.**

- `publish-backend-image`: set `DOCKER_CONFIG` to a job-owned temporary directory for the login and
  push, so the runner's shared store is never written.
- `deploy-app`: the same inside the SSH block — export `DOCKER_CONFIG` to a temporary directory,
  run `compose pull` under it, remove it at the end.

**Scoping, not a cleanup step.** A `docker logout` in an `always()` block still leaks whenever the
job or SSH session dies between login and cleanup — and with three parallel runner slots and twelve
apps per host, that is the observed state rather than a corner case.

Required tests, added to the narrow set: assert that neither action writes to the default credential
location — i.e. that `DOCKER_CONFIG` is set before any `docker login`. Assert the **presence** of the
scoping, since its absence is what caused this and would be silent again.

### The pattern worth naming

This is the third instance in three days of the same shape: **a new component writes to state shared
with others, and nothing cleans up after it.** First the build cache on main-prod (INF-11), then the
orphaned artifact trees (GC-8/GC-9), now the credential store on the runner and every deploy target.
Worth asking explicitly of any new component: *what does this leave behind on a machine that belongs
to someone else too?*
