# CI-10 — Publish to GHCR with the built-in `GITHUB_TOKEN`, not a new org secret

Status: planned · Tier: 2, prod-infra · Target repo: workflow-templates (main) + consuming app repos · Datum: 2026-08-08 · Supersedes CI-9's secrets decision

## A. Envelope (Expertenchat — authoritative WHAT/WHY)

### Goal

Remove `GHCR_TOKEN` from the CI-9 design and publish with the `GITHUB_TOKEN` GitHub already issues
per workflow run. Introduce **no new credential** — nothing to create, store, rotate, or leak.

### Why — CI-9's fix works, but its cost was mispriced

CI-9's reviewer correctly found a real P1: GitHub caps a reusable workflow's `GITHUB_TOKEN` at what
the **caller** grants, and every app repo's `ci.yml` grants only `contents: read` (verified directly
— e.g. `cockpit/.github/workflows/ci.yml:8-9`). The chosen remedy was a new org-level `GHCR_TOKEN`,
justified by "zero app-repo changes".

That justification does not survive contact with the estate's secret custody:

- `webapp-management/secrets.yaml` supports `target_scope: repo` and `target_scope: env` — **no org
  scope**. `sync-secrets` therefore cannot manage an org secret at all.
- It would be created by hand in the GitHub UI: no Proton entry, no coverage by
  `secret-rotation-reminder.yml`, no record of scope or purpose.
- The estate's documented pattern for a GitHub credential is a fine-grained PAT in Proton with
  `target_scope: repo` + `exclude_from_env: true` (`ROUTINES_GH_PAT`, `CLAUDE_CODE_OAUTH_TOKEN`),
  next to the explicit note *"Never a classic org-wide PAT."*
- Following that pattern properly would need a declaration in **each** app repo — because
  `secrets: inherit` resolves against the *calling* repo, so a webapp-management repo secret never
  reaches hram's CI.

So both principled options cost roughly a dozen small per-repo edits. Given equal effort, prefer the
one that adds **no credential at all**: a `GITHUB_TOKEN` is minted per run, scoped to its repository,
and expires with the job.

### Verified precondition

The organisation's container package list is **empty** (operator-confirmed, 2026-08-08). Consistent
with CI-9's own finding that `docker push` appeared nowhere before it — nothing has ever been pushed
to ghcr.io. This matters: the first push with `packages: write` **creates** the package and grants
the pushing repository admin on it automatically. **No manual package-permission setup is required.**

The case that would have required an admin step — an existing, unlinked package — does not apply.

### Scope

**1. `app-ci.yml`**

- Authenticate the registry login with `GITHUB_TOKEN` instead of `GHCR_TOKEN`; remove the
  `GHCR_TOKEN` secret input and its guard. Keep the `IMAGE_TAG` guard — an empty tag must still
  refuse to publish.
- Add the auto-link label to the build so the package↔repository link is deterministic rather than
  incidental:
  `--label org.opencontainers.image.source=https://github.com/${{ github.repository }}`.
  **This belongs in the shared workflow, not in twelve Dockerfiles** — no Dockerfile currently sets
  it, and adding it centrally covers every app at once.

**2. `deploy-app/action.yml`**

- Same swap on the pull side.
- Preserve the hygiene CI-9 established: whatever token is used must be stripped from the `.env`
  payload (`:380`'s `del(.GHCR_TOKEN)` equivalent) so it never lands on a server's disk, and the two
  build secrets must still be removed on non-fallback deploys (`:384-386`).

**3. Consuming app repos — the one unavoidable per-repo change**

Add `packages: write` to the workflow-level `permissions:` block of each app's `ci.yml` (and the
deploy caller, so the pull side is covered). GitHub's cap makes this structural: no change inside
`workflow-templates` can grant a permission the caller withheld.

### Non-goals / do-not-touch

- **NOT** reintroducing `GHCR_TOKEN` or any org-level secret.
- **NOT** making the packages public. Private is correct — the servers pull with a token forwarded
  from the deploy workflow.
- **NOT** editing Dockerfiles. The label goes in the shared build command.
- **NOT** CI-9's transport design (SHA tags, the `--build` fallback, `compose pull`). That stands;
  only the credential changes.
- **NOT** the deploy rollout itself — the first pull-based deploy stays operator-gated.
- Not auth/permission logic in the applications, schema, or app behaviour.

### Prototype and rollout

**cockpit is the operator-chosen prototype, and it fits CI-9's "staging first" without exception.**

- `project.yaml` declares a **`staging` environment on the `staging` server**
  (`staging-cockpit.bigler-consult.ch`), separate from `production` on main-prod. The first
  pull-based deploy therefore goes to staging-cockpit, and a failure there touches only the staging
  box — cockpit's own `env_overrides` comment confirms *"staging cockpit is not on main-prod"*.
- It is also the **hardest** pull on the estate: cockpit carries the largest image (the spaCy
  models, ~2 GB — see cockpit **IMG-1**). That makes it a genuine stress test rather than a soft
  one, which is why it is a good prototype rather than merely a convenient one.
- Production follows only after staging proves out — and cockpit's production target is main-prod,
  the box this whole workstream exists to relieve.

**Ordering matters and this is a coordinated rollout, not one commit.** Every `@main`-pinned app
(cockpit, hram, jg-ferien, survey_app — spesix pins a SHA and is unaffected) currently fails at
CI-9's publish step because `GHCR_TOKEN` does not exist. Landing this WO's `workflow-templates` half
does not by itself fix them: each repo stays broken until it grants `packages: write`. Land the
shared half and cockpit's `permissions:` line together, prove it, then roll the remaining repos.

### Acceptance

- A cockpit CI run publishes `ghcr.io/bigler-webapps/cockpit-backend:<sha>` using only
  `GITHUB_TOKEN` — no `GHCR_TOKEN` anywhere in the run.
- The subsequent **staging** deploy of cockpit pulls that digest and starts it with **no build step
  on the target** — read from the deploy log, not inferred. A green deploy that silently took the
  `--build` fallback would look identical from the outside and prove nothing.
- The created package is **linked to the cockpit repository** (the label works) and **private**.
- No `GHCR_TOKEN` remains in `app-ci.yml`, `deploy-app/action.yml`, or any documentation as a
  required secret.
- The token does not appear in the generated `.env` on any target.

### Required tests to WRITE (narrow)

- Structural: `app-ci.yml` logs in with `GITHUB_TOKEN` and references no `GHCR_TOKEN`; the
  `IMAGE_TAG` guard survives the edit.
- Structural: the build command carries the `org.opencontainers.image.source` label pointing at
  `github.repository`.
- The `.env` payload filter still strips the registry token and, on non-fallback deploys, both build
  secrets. Assert the **absence** — this is the property most likely to be lost while swapping token
  names, and its loss would be silent.

Scoped to the existing `.github/scripts/` structural tests. Not an estate render.

### Risks

- **The rollout window is a broken-CI window.** Between landing the shared half and granting
  `packages: write` in a given repo, that repo's CI fails at publish. It already fails today, so this
  does not make things worse — but it does mean the WO is not finished when `workflow-templates` is
  green.
- Do **not** "solve" that by making the publish step skip when it lacks permission. A silently
  skipped publish produces a deploy that pulls a tag which was never pushed — a late, confusing
  failure instead of an early, obvious one.
- `GITHUB_TOKEN` cannot push to a package owned by a *different* repository. Irrelevant now (the
  registry is empty), but it means a package must never be hand-created out-of-band later.
- Package visibility defaults to private; verify rather than assume, since a public research-adjacent
  image would be an unintended disclosure.

### 2. `workflow-templates/.github/actions/deploy-app/action.yml`

Local `.env`-generation step (`:359-393`): the `del(.GHCR_TOKEN)` at `:380` becomes dead code once
the org secret no longer exists — remove that specific `del()` clause. The `^(SSH_|B2_|RESTIC_|
GITHUB_|TS_)` regex on the same line already strips anything named `GITHUB_*`, which is why
`GITHUB_TOKEN` needs **no equivalent explicit `del()`** — it never reaches `.env` in the first place.
Keep `del(.HRAM_ENGINE_READ_TOKEN, .VITE_APP_MUI_LICENSE_KEY)` at `:386` (still required, still
stripped on non-fallback deploys) — do not touch that line.

Remote-login step (`:500-590`): replace the `GHCR_TOKEN="$(printf '%s' "$SECRETS_CONTEXT_RAW" | jq
-r '.GHCR_TOKEN // empty')"` extraction (`:518`) and its guard (`:520-522`) — the token no longer
travels through `secrets_context_json` at all. Add `GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}` (or
equivalently `${{ github.token }}`) directly to the step's own `env:` block, guard it the same way
(`[ -n "$GITHUB_TOKEN" ] || { ...; exit 1; }`), then forward it through the SSH heredoc's
local-interpolate/remote-escape split exactly like `GHCR_TOKEN` was (`:537`, `:585`) — rename the
remote variable too so nothing in the diff still says `GHCR_TOKEN`. `SECRETS_CONTEXT_RAW` may become
unused in this step once the extraction is gone — remove the now-dead `env:` entry and `unset` line
if nothing else in the step needs it (check before deleting: `USE_BUILD_FALLBACK`/`IMAGE_TAG` reads
don't depend on it).
