# CI-21 — `pnpm/action-setup`'s shared per-runner install destination races between concurrent job slots

Target repo: `workflow-templates` (branch `main`). Touches `.github/workflows/app-ci.yml` (`frontend`
job) and a new structural test under `.github/scripts/`.

Tier: **3** — CI is a sensitive surface per `AGENTS.md`; `app-ci.yml` is the reusable workflow every
app repo's CI consumes.

Split out of survey_app's `SVA-CI-2` (`survey_app/WORK_ORDERS.md`) — see that WO and the `WORK_ORDERS.md`
CI-21 register row for the original incident (a `pnpm: command not found`, exit 127, on
`netcup-runner-1`) and the source-level root-cause analysis. Not re-derived here.

---

## A. Envelope

### Goal & expected outcome

- Ziel: stop `pnpm/action-setup@v4.4.0`'s install step from racing with itself across concurrent job
  slots on the same self-hosted runner host.
- Expected outcome: the `frontend` job's `pnpm/action-setup` step installs into a destination that is
  unique per job run (e.g. `${{ runner.temp }}/setup-pnpm`) instead of the action's shared default
  (`~/setup-pnpm`), so one job's `rm(dest)`-then-reinstall (`run.ts`, unconditional on every
  invocation, verified at tag `v4.4.0`) can no longer delete the binary out from under a different,
  concurrently-running job on the same runner. No change to which pnpm version gets installed or how
  it's invoked afterward.

### Correction to the register row

The CI-21 row (and the incident writeup it inherited from `SVA-CI-2`) frames the race as "`frontend` +
`security` both [call this action], every run." As of the current `app-ci.yml`, that's not accurate:
the `security` job never calls `pnpm/action-setup` — it runs `corepack enable` directly before `pnpm
audit` (`app-ci.yml:330-336`), a different provisioning path. Only the `frontend` job
(`app-ci.yml:344-346`) invokes the action. The actual race is therefore between concurrent invocations
of the `frontend` job itself — e.g. two different app repos' CI runs (or a PR + a push trigger)
landing their `frontend` job on two of the runner's slots at the same time — not between `frontend`
and `security` within one workflow run. This narrows the fix target to the one step; it does not
change the underlying diagnosis (the action's own shared-`dest`-by-default behavior, verified against
its source).

### Scope

- In scope: `app-ci.yml`'s `frontend` job, `pnpm/action-setup` step only (~line 344-346) — add a
  `dest` input pointing at a per-job-unique path (`${{ runner.temp }}` is the candidate already named
  in the register row).

### Non-goals / do-not-touch

- Not the `security` job — it doesn't call this action; there's nothing to change there (see
  correction above).
- Not `corepack enable`'s own install path in the `security` job — plausible it also writes into a
  shared location, but there's no incident evidence tying it to a race, and it's a different,
  unverified code path. Leave it.
- Not an estate-wide fix for `packageManager`-vs-`pnpm-version` drift in other consumer repos.
  `survey_app`'s own instance was closed as `SVA-CI-2`; whether the same drift exists elsewhere is a
  separate investigation (per-repo `package.json` changes, not a `workflow-templates` change) and does
  not belong in this WO.
- Not a runner-side change (slot count, a mutex/locking mechanism) — per-job destination isolation is
  the action's own supported customization point and should be sufficient on its own.

### Tier · precondition

- Tier: **3** — CI infrastructure, sensitive surface per `AGENTS.md`'s tiering table.
- Precondition: none known.

### Risks

- **Risk 1 — `${{ runner.temp }}` may not be genuinely unique per concurrent job slot on this specific
  self-hosted runner setup.** If the runner's 3 slots share one `_work`/`_temp` folder (e.g. spawned
  from a single runner process rather than 3 separate `actions-runner` registrations), `runner.temp`
  would not isolate the race and the fix would be a no-op. Confirm how `netcup-runner-1`'s slots are
  actually registered before or while implementing — this is a fact about the runner host, not
  something derivable from this repo's files alone.
- **Risk 2 — minor performance regression.** A per-job `dest` means pnpm is reinstalled fresh on every
  `frontend` run instead of potentially reusing a warm shared install. Acceptable trade-off for
  correctness; not worth engineering around here.
- **Risk 3 — confirm `dest`'s accepted semantics on the pinned tag.** The register row already
  verified this against `pnpm/action-setup`'s `run.ts` at tag `v4.4.0`; re-confirm nothing about
  `dest` interacts with the action's internal caching/PATH-exporting behavior before landing.

### Required tests to WRITE

A structural regression test in `.github/scripts/`, following the existing
`test_app_ci_composite_checkout.py` pattern (regex-based assertions against the raw workflow YAML
text, not a YAML parse/execute):

- the `frontend` job's `pnpm/action-setup` step carries a `with.dest` value referencing a per-job-unique
  path (e.g. containing `runner.temp`), anchored to that specific step (not merely present somewhere
  in the file) so it can't pass by matching an unrelated step;
- mutation-tested per `AGENTS.md`: the test must be shown to FAIL against the current (unfixed)
  `app-ci.yml` and against a version where the `dest` line is present but detached from the
  `pnpm/action-setup` step — not merely shown to pass against the fixed file.

### Verified facts (resolve both open Risks in Part A)

- **`pnpm/action-setup`'s `dest` input is real**, confirmed against the pinned SHA's `action.yml`
  (`gh api repos/pnpm/action-setup/contents/action.yml?ref=f40ffcd9367d9f12939873eb1018b921a783ffaa`):
  `dest` (optional, `default: ~/setup-pnpm`) — "Where to store pnpm files". Resolves Risk 3.
- **`${{ runner.temp }}` IS genuinely unique per concurrent job slot on `netcup-runner-1`** — resolves
  Risk 1. Verified directly in this repo's own `ansible/roles/github_runner/`:
  `tasks/main.yml` gives each of the `github_runner_slots` (3, `host_vars/netcup-runner-1.yml`) its
  own **fully separate copy of the runner tree** at `{{ github_runner_base_dir }}/slot-<N>/`
  ("Initialise per-slot runner directories"), and `templates/gh-runner@.service.j2` sets
  `WorkingDirectory={{ github_runner_base_dir }}/slot-%i` and runs that slot's own `run.sh`. Each
  slot is therefore an independent runner process rooted in its own directory tree, so the runner
  binary's `RUNNER_TEMP` (`<runner root>/_work/_temp`) is per-slot-isolated already — `${{
  runner.temp }}/setup-pnpm` will not collide across slots.

- Do not change `inputs.pnpm-version` handling or any other `with:` key on this step.
