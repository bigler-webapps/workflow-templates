# CI-16 — Retire the PostGIS CI database default; declare it only where geo is real

## Part A — Envelope

**Target repo:** `workflow-templates` (trunk `main`)
**Tier:** 3 (CI)
**Date:** 2026-08-17

### Goal

`app-ci.yml`'s `db-image` input defaults to `postgis/postgis:14-3.1`, so every app repo that does
not override it runs its CI database on a PostGIS image. Exactly three repos in the estate need
PostGIS. The rest inherit it silently, pulling a heavier image on a shared, disk-constrained runner
for a capability they never use.

Flip the default to plain `postgres:14`, and make the PostGIS dependency explicit in the three
repos that actually have one.

Expected outcome: `db-image` defaults to `postgres:14`; hram, jg-ferien and kerzenziehen declare
`db-image: postgis/postgis:14-3.1` in their own `ci.yml`; every other consumer runs its CI on a
plain Postgres service; and no consumer's CI is red at any point in the sequence.

### Measured findings this rests on (staging, 2026-08-17)

Read-only measurement, not inference:

- 13 of 14 staging app databases run `postgis/postgis:14-3.1` and carry `postgis`,
  `postgis_topology`, `postgis_tiger_geocoder` and `fuzzystrmatch`. These are installed by the
  **image** at initdb, not by any application — which is why apps with no geo code have them too.
- App-owned geometry columns exist in **hram only** (`geometry_columns` → `public|4`). In every
  other database all 12 geometry columns sit in the `tiger` schema, i.e. they belong to the
  geocoder extension itself.
- Exactly three repos declare GeoDjango in `backend/backend/settings.py`: hram (`:37` ENGINE),
  jg-ferien (`:18` `GIS_APPS`, `:63` ENGINE), kerzenziehen (`:9` `INSTALLED_APPS`, `:36` ENGINE).
- jg-ferien and kerzenziehen inherit those settings into CI — `backend/backend/test_settings.py`
  does `from .settings import *`. Django's PostGIS backend installs the extension when it creates
  the test database, so on a plain Postgres service their CI fails **at test-database setup**, not
  in a test assertion. This is why they need the pin even though they store no geometry.
- Only cockpit overrides `db-image` today (`pgvector/pgvector:pg14`, its `ci.yml:20`).

### Scope

1. `hram/.github/workflows/ci.yml` — add `db-image: postgis/postgis:14-3.1` to the existing `with:`
   block. Purely additive; preserves today's behaviour exactly.
2. `jg-ferien/.github/workflows/ci.yml` — same line.
3. `kerzenziehen/.github/workflows/ci.yml` — same line.
4. `survey-routing` — **not cloned in the local workspace**, so it could not be checked. Inspect it;
   if its settings declare `contrib.gis` or the postgis ENGINE it gets the same pin as 1-3, and if
   not it needs nothing. Do not assume either way. Apply the same check to any other consumer of
   `app-ci.yml` that is not present locally.
5. `workflow-templates/.github/workflows/app-ci.yml:25` — change the `db-image` input default from
   `'postgis/postgis:14-3.1'` to `'postgres:14'`.

### Ordering — hard, and the point of the WO

Consumers reference the reusable workflow as `app-ci.yml@main`. The default therefore changes for
the whole estate the moment step 5 lands on workflow-templates' `main`; there is no staging buffer
for a shared workflow. **Every pin from steps 1-4 must be on its repo's trunk before step 5 is
pushed.** A repo whose pin is not yet there has red CI from that moment.

### Non-goals / do not touch

- **No `docker-compose.yml` change in any app repo.** The runtime database image and the `postgis`
  extension inside the live databases are a separate, later step. This WO is CI only.
- **Do not remove `GIS_APPS` / `contrib.gis` / the postgis ENGINE from jg-ferien or kerzenziehen.**
  The measurement shows nothing is behind it, but removing it changes the container's import path
  and needs its own staging deploy. Here those two get pinned, not cleaned.
- **No Dockerfile or apt changes anywhere.** `build-essential`, `libpq-dev`, `libgdal-dev`,
  `libproj-dev`, `libgeos-dev` and the dead `GDAL_LIBRARY_PATH` export belong to the separate
  build-toolchain workstream. Two work orders must not edit the same Dockerfile lines.
- **Do not touch cockpit's `pgvector/pgvector:pg14` override.**
- **Postgres stays at major 14.** `postgres:14`, never 15 or 16 — a major bump carries an
  incompatible PGDATA and is a separate change.
- Do not rename or retype the `db-image` input, and do not touch its single consumer at
  `app-ci.yml:95`.

### Risks

- **Estate-wide red CI** if step 5 lands before any of steps 1-4. This is the reason the ordering
  clause is part of the scope rather than a note.
- **A consumer missed.** The completeness claim rests on a grep of `backend/backend/settings.py`
  across locally-cloned repos. Two traps: `survey-routing` is not cloned (step 4), and the
  workspace root `.gitignore` lists every app repo, so a search rooted at `webapps` silently
  returns **zero hits for all app code**. Re-verification must run per repo or with ignore rules
  disabled — a clean result from a root-level search is not evidence of absence.
- **First-run image pull.** `postgres:14` is not currently on the shared netcup runner; the first
  run after the flip pulls it. Cheap, but not free.

### Tests to write

**None.** This is a CI configuration change with no application behaviour to assert, and a new test
would not catch the failure mode (which is a workflow-level service image, observable only by
running CI).

One exception that is a fix rather than a new test: `.github/scripts/test_app_ci_*.py` (CI-14)
contains structural assertions over `app-ci.yml`. If one of them asserts the `db-image` default
string, update that assertion as part of step 5.
