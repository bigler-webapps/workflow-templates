# CI-18 — `deploy-app` reports success without checking that the stack survived the deploy

Target repo: `workflow-templates` (branch `main`). Touches `.github/actions/deploy-app/action.yml`
and `.github/scripts/test_deploy_app_action.py`.

Tier: **3** — CI is a sensitive surface per `AGENTS.md`; this action runs on every app's deploy,
including production. Codex is recorded `unavailable` for 2026-08-20 (`.claude/codex-status.md`), so
the Orchestrator authors directly and the independent review is mandatory rather than routine.

Handed over from cockpit's `OBS-29` (dropped 2026-08-20). See the `WORK_ORDERS.md` CI-18 register
row for the full incident writeup and the four rejected alternatives (health-endpoint poll variants)
— not re-derived here.

---

## A. Envelope

### The incident

On 2026-08-20 cockpit's `beat` container entered a crash loop after a deploy: an unpinned
`django-celery-beat` resolved backwards to a 2020 release and every scheduler tick died. `Deploy App`
reported success in 57 seconds and stayed green while the scheduler was dead for 2h25m. A green deploy
is a claim about the deployed state, and that claim was false.

### The fix

After the recreate and the migration step, and before the INF-51 image-cleanup block and the final
success line, assert that no container of the project's own stack (`compose ps -q` — never host-wide)
is in Docker's `Restarting` state. If any is, print its name and `exit 1`, which fails the deploy step
and — because it runs before INF-51's cleanup — leaves the replaced image in place for rollback.

Generic across every app on the action: no app-specific knowledge, no new secret, no health endpoint.
Rejected alternatives (parameterised liveness poll, wait-out-the-freshness-window, boot-relative
heartbeat) are costed in the register row; the deciding argument is that a 10-minute liveness freshness
window reads green immediately after a 57-second deploy that killed the service it is meant to catch.

### Scope

1. `deploy-app/action.yml`: insert the health-check block between the migration step and the existing
   INF-51 replaced-image cleanup.
2. `test_deploy_app_action.py`: structural + mutation tests, extracting the real block out of the
   action file (same pattern as INF-51's `_extract_cleanup_block`) rather than reimplementing the
   logic under test.

### Non-goals

- Not a health-endpoint check of any kind — rejected per the register row.
- Not urgent and should block nothing beyond a genuinely restart-looping container; a normal deploy is
  unaffected.
- Not a retry or backoff mechanism — this is a single point-in-time check right after the stack comes
  up and migrations run, not a sustained watch window.

### Risks

**Risk 1 — a container that starts healthy and crashes minutes later is not caught.** The check runs
once, immediately after migrations. The register row's own cost-benefit (~14 minutes plus unambiguous
attribution, on an incident class seen once) accepts this; a sustained watch window was traded away
deliberately in the same alternatives analysis that rejected the health-endpoint poll.

**Risk 2 — this can fail a deploy that would otherwise have self-healed.** A container that restarts
once during normal startup and is `running` by the time this check runs is unaffected — `Restarting`
is Docker's transient state for a container actively bouncing under its restart policy, not a marker
of "restarted at some point". No case of a false positive on ordinary startup was found in review.

### Tests

Structural, mutation-tested per the register row's explicit constraint ("shown to FAIL against a
stack with a restarting container, not merely to pass against a healthy one"), in
`test_deploy_app_action.py`:

- a healthy stack passes and execution reaches past the check;
- a stack with one restart-looping container (reproducing the `beat`-equivalent incident shape) FAILS
  the script, names the container, and does not reach past the check;
- the check is scoped to `compose ps -q`, never `docker ps -aq`;
- ordering: after migrations, before both the INF-51 cleanup and the final success line.

### Verification

No live staging run required — this is a structural addition to a shell block already exercised by
INF-51's own live verification of the surrounding script. The next ordinary deploy to any app exercises
the new check in production conditions; nothing here needs a dedicated dispatch.

### Review

`reviewer` (Sonnet) and `sec_reviewer` (Sonnet) ran independently and concurrently against the full
diff, both cleared it.

`sec_reviewer`: no findings. Confirmed the addition is purely read-only diagnostics (`docker
inspect`/`compose ps -q` against the already-reachable local host, identical scope to the INF-51 block
beside it), no new secret, no new network reach, no privilege widening. Empirically verified fail-closed
semantics under `set -euo pipefail` with a local bash repro. Container names cannot carry injection
payloads (Docker enforces `[a-zA-Z0-9][a-zA-Z0-9_.-]+` at the daemon level) and the extracted value is
only ever echoed, never eval'd.

`reviewer`: two P3s, both informational.
- R1 (fixed): `RESTARTING_NAMES="$(...)"` lacked the `|| true` guard used by the two structurally
  identical pipelines in the neighboring INF-51 block, so a transient `docker inspect` race (a container
  removed between `ps -q` and `inspect`) would abort the deploy step with a raw shell error instead of
  this block's own diagnostic message — still fail-closed either way, just a less clear failure mode.
  Guard added to match the sibling pattern.
- R2 (accepted, not fixed): the check only catches Docker's transient `Restarting` state, not a
  container that has exhausted its restart policy and settled into `Exited`/`Dead`, nor one that is `Up`
  but failing a defined `HEALTHCHECK`. This is the documented scope limit already named as Risk 1 above,
  not a new gap.
