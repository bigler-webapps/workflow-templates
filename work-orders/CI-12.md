# CI-12 — Roll the publish-then-pull deploy to the remaining eleven repos

Status: planned · Tier: 2 · Target repo: workflow-templates (main) + eleven app repos · Datum: 2026-08-09 · Completes the CI-9/CI-10/CI-11 rollout

## A. Envelope (Expertenchat — authoritative WHAT/WHY)

### Goal

Bring the eleven repos still on old `deploy-app` pins onto `v2.9.0` **with** the CI-10/CI-11
changes they depend on, so main-prod stops building images for them.

### Why — and why this is not just a version bump

Four repos (cockpit, hram, jg-ferien, survey_app) are live on `v2.9.0` and verified. Eleven are not:

| Current `deploy-app` pin | Repos |
|---|---|
| `v2.4.4` | Kira, bigler-consult, innoservice, kerzenziehen, reimbursements, spesix, survey_contact_app, webapp-template, yopoulab-hhs-2026 |
| `v2.5.4` | hpc-bridge |
| `v2.4.1` | webshop-guenter |

**Bumping only the pin would be actively harmful.** `v2.9.0`'s `deploy-app` pulls instead of
building; without CI-11's publish step in the repo's own `main.yml` there is no producer, and the
deploy fails exactly as the four did on 2026-08-08 (harmlessly — containers keep running — but red
on every push).

**And there is a latent failure already present, independent of any bump.** Every one of these repos
except spesix pins `app-ci.yml@main`, so they already receive CI-10's publish step — but their
`ci.yml` grants only `contents: read`. Because `ci.yml` runs on `pull_request` only, nobody has hit
it yet: it fires on their **next promotion PR**. Verified: **none of the eleven has `packages` in
any `permissions:` block.** Fixing that is part of this WO, not a follow-up.

### Scope — per repo

1. `ci.yml`: add `packages: write` to the workflow-level `permissions:`.
2. `main.yml`: add `packages: write` to `permissions:` (none of the eleven has it) **and** the
   publish step immediately before the `deploy-app` step, mirroring cockpit's landed shape.
3. Bump both pins to `v2.9.0`.

### The four repos that are not uniform — handle each deliberately

- **spesix** pins `app-ci.yml` to SHA `a114d6e` (2026-06-25), so it never receives CI-10's publish
  step. **Leave that pin alone** — bumping it to `@main` changes spesix's CI behaviour beyond this
  WO. Consequence: spesix needs no `ci.yml` change; only `main.yml` and the `deploy-app` pin.
- **yopoulab-hhs-2026** has **no `ci.yml` at all** and no `app-ci` pin. `main.yml` and the pin only.
- **webshop-guenter** has a `ci.yml` but no `app-ci` pin — it does not use the shared CI. Same
  treatment as yopoulab: `main.yml` and the pin only. Do not wire it into `app-ci.yml` here.
- **webapp-template** is the template repo; its deploy job is skipped by the `is_template` guard, so
  it **cannot be verified by a green deploy**. Bump it anyway — new repos must start correct — and
  say plainly in the report that this one is unverified by construction.

### Non-goals / do-not-touch

- **NOT** changing `workflow-templates` itself. `v2.9.0` is the target; if something in the shared
  half needs fixing, that is a new WO, not a silent edit here.
- **NOT** bumping spesix's `app-ci.yml` SHA pin, and **NOT** adding `app-ci` to webshop-guenter or
  yopoulab.
- **NOT** test-gating any deploy — CI-11's non-goal stands unchanged for all eleven.
- **NOT** promoting anything to `main`. This lands on each repo's trunk only.
- Not app behaviour, schema, auth, or dependencies.

### Acceptance

- Each of the eleven carries `packages: write` in both workflows (where the workflow exists), the
  publish step before `deploy-app` in `main.yml`, and `v2.9.0` on both pins.
- For at least one repo per pin-group (`v2.4.4`, `v2.5.4`, `v2.4.1`), a real push to `develop`
  publishes and deploys green, with **no build step on the target host** — read from the log.
- webapp-template is reported as bumped-but-unverifiable, not silently counted as green.

### Required tests to WRITE (narrow)

Structural only — this is a mechanical repetition of a shape already proven three times, and no new
logic is introduced:

- Per repo: the publish step precedes the `deploy-app` step in the same job.
- Per repo: both pins are `v2.9.0` (catch a half-bump, which would be the most likely slip across
  eleven repos).
- The special cases stay special: spesix's `app-ci` SHA pin unchanged; webshop-guenter and yopoulab
  gain no `app-ci` reference.

No app tests. This changes no application code, and saying so is the correct answer.

### Risks

- **Operator chose all eleven in one pass, without a staged stop.** If the pattern is wrong, eleven
  repos go red at once rather than one. Accepted deliberately: the shape is identical to cockpit's
  landed and verified `main.yml`, and the failure mode is non-destructive (containers keep running
  on their current image). Copy cockpit's shape rather than re-deriving it.
- The most likely slip is a **half-bump** — `deploy-app` moved to `v2.9.0` while the publish step or
  a `permissions:` line is missed. That produces exactly the 2026-08-08 failure. The structural test
  above exists for this.
- Eleven repos each building a full production image on the shared runner is new sustained load.
  INF-11's daily 20 GB reclaim is what bounds it; watch the runner's disk over the first days.
- **Tier 2 is an informed deviation.** `deps/CI` is a Tier-3 entry criterion in `AGENTS.md`; the
  operator classified this Tier 2 on 2026-08-09 on the grounds that it is mechanical repetition of a
  verified pattern with no new design. Recorded here so the classification is traceable, not
  accidental.
