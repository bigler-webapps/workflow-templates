# A. Envelope

## Goal & expected outcome
- Ziel: `app-ci.yml`'s "Publish backend image to GHCR" step must resolve the `publish-backend-image`
  composite action against **this repo** (`workflow-templates`), not against whichever repo called
  the reusable workflow.
- Expected outcome: a PR against any app repo that calls
  `bigler-webapps/workflow-templates/.github/workflows/app-ci.yml@main` runs the "ci / backend" job
  to green through the publish step, instead of failing with
  `Can't find 'action.yml', 'action.yaml' or 'Dockerfile' under '.../.github/actions/publish-backend-image'`.

## Scope + non-goals
- In scope: `workflow-templates/.github/workflows/app-ci.yml` only — specifically the "Publish
  backend image to GHCR" step (currently line 185) and whatever precedes it needed to make the
  composite resolve correctly.
- Explicit non-goals / do-not-touch:
  - Do not touch `restore-cross-server.yml` or `staging-health.yml` — both were already verified
    unaffected (`restore-cross-server.yml` already uses the correct checkout-into-subfolder pattern;
    `staging-health.yml` has no local composite reference at all).
  - Do not touch any app repo's `ci.yml`/`main.yml` — this is a `workflow-templates`-only fix; every
    caller already references `app-ci.yml@main`, so the fix propagates automatically on next PR run.
  - Do not touch the `publish-backend-image` composite action's own `action.yml` — it has no internal
    local-path references and does not need to change.
  - Do not change the CI-12 deploy-time publish/deploy steps in any app's `main.yml` — those already
    reference composites via the full cross-repo path (`bigler-webapps/workflow-templates/.github/actions/...@v2.9.0`)
    and are unaffected by this bug.

## Tier · precondition / gate
- Tier: 3 (CI/CD surface, per `AGENTS.md` Tiering table entry criterion "deps/CI"). Operator gave
  explicit Gate #0 approval on 2026-08-09 after the finding was independently verified (confirmed
  root cause: `app-ci.yml:112` checks out the caller repo at the job's default root path; the local
  `uses: ./.github/actions/publish-backend-image` at line 185 therefore resolves against that
  checkout, which has no such directory for a cross-repo caller).
- No precondition — this can land standalone. It blocks every `develop → main` promotion PR in the
  estate today (silently, since `ci.yml` only runs on `pull_request`, including promotion PRs against
  `main`), so land it before the next promotion is attempted.

## Risks
- **Blast radius if wrong:** every app repo's CI depends on `app-ci.yml`. A bad fix breaks CI
  estate-wide the same way the current bug does, just differently. Mitigate by mirroring the
  already-proven pattern in this same repo (`restore-cross-server.yml`) rather than inventing a new
  one.
- **Docker build-context pollution:** the fix adds a second checkout into a subfolder inside the
  caller's workspace root. `app-ci.yml`'s own "Build backend image" step (line 121) and the
  composite's internal build both use `inputs.build-context` (default `.`, i.e. the caller repo
  root) as the Docker build context — a stray subfolder under that root would get included in the
  build context tarball. Check each caller's `.dockerignore`/`.gitignore` is not a concern here
  because Docker's context-send happens BEFORE this checkout in `app-ci.yml`'s own first build (line
  121-150, already built before the publish step runs) — but the composite's OWN build (inside
  `publish-backend-image`, for `backend_target != ''` callers that need a full-image rebuild) runs
  AFTER this new checkout exists on disk, so it is a live concern there. Verify the composite's build
  step's context does not silently balloon or fail; if it's a real problem, name the subfolder
  something already covered by a wildcard `.dockerignore` entry (e.g. `.wt-checkout` — most repos'
  `.dockerignore` excludes dotfiles broadly) or explicitly add a `.dockerignore`-scoped exclusion as
  part of this fix.
- **Ref-pin drift:** the new checkout of `workflow-templates` must be pinned to a literal SHA (this
  repo's established convention, see `restore-cross-server.yml`'s own comment block on why — a
  moving `@main` checkout would defeat the whole point of a reusable workflow having a stable,
  reviewable version). Use `1efa2e0d985b5d9e75e95c3a79c500a27fa5bcdb` (tag `v2.9.0`, the same
  commit already pinned by every app's `deploy-app@v2.9.0`/`publish-backend-image@v2.9.0` references
  from CI-12) so there is exactly one "current" `workflow-templates` version referenced across the
  whole estate, not two independently-drifting pins.

## Required tests to WRITE
- A structural regression test under `.github/scripts/` (this repo already has
  `test_deploy_app_action.py` in this style — follow it) asserting:
  1. `app-ci.yml` contains a `checkout` step with `repository: bigler-webapps/workflow-templates`
     BEFORE the "Publish backend image to GHCR" step.
  2. That checkout step's `with:` block declares a non-default `path:` (i.e., it is NOT checked out
     to the workspace root — this is the regression the bug itself was: a root-level checkout would
     either fail on "already exists" or silently overwrite the caller's own checkout, both wrong).
  3. The "Publish backend image to GHCR" step's `uses:` value starts with `./` and includes that same
     `path:` value as a path segment (i.e., it points INTO the checked-out subfolder, not at the
     caller-repo root `./.github/actions/...`).
  4. The checked-out `ref:` is a 40-character literal SHA (not `main`, not a short SHA, not a tag
     name) — guards against a future edit reintroducing a floating ref.
- No behavioral/integration test is possible from this repo in isolation (the bug only reproduces
  when `app-ci.yml` is invoked cross-repo by an actual caller) — the real acceptance test is a live
  PR in an app repo going green, which the Orchestrator verifies post-merge (see Part B).

# B. Implementation map

## Context package

**File to change:** `workflow-templates/.github/workflows/app-ci.yml`

**Current broken step (line 179-194):**
```yaml
      - name: Publish backend image to GHCR
        id: publish_backend_image
        uses: ./.github/actions/publish-backend-image
        with:
          image_tag: ${{ steps.resolve_sha.outputs.sha }}
          github_token: ${{ secrets.GITHUB_TOKEN }}
          backend_dockerfile: ${{ inputs.dockerfile }}
          backend_build_context: ${{ inputs.build-context }}
          backend_target: ${{ inputs.backend-target }}
          hram_engine_read_token: ${{ secrets.HRAM_ENGINE_READ_TOKEN }}
          vite_app_mui_license_key: ${{ secrets.VITE_APP_MUI_LICENSE_KEY }}
          existing_image: ${{ inputs.backend-target == '' && env.CI_IMAGE || '' }}
```

**Why it breaks (verified):** `app-ci.yml` line 112 (`uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683`,
no `repository:` override) checks out the CALLING repo (e.g. `hram`, `hpc-bridge`) at the job's
default workspace root, because this job is invoked as `workflow_call` from those repos'
`ci.yml` (`uses: bigler-webapps/workflow-templates/.github/workflows/app-ci.yml@main`). The local
`uses: ./.github/actions/publish-backend-image` on line 185 therefore resolves relative to THAT
checkout — which has no `.github/actions/publish-backend-image` directory — producing
`Can't find 'action.yml' ... under '.../.github/actions/publish-backend-image'`.

**Reference fix already proven in this same repo — `restore-cross-server.yml` (lines 156-198):**
```yaml
      - name: Checkout workflow-templates (for composite actions)
        uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683  # v4.2.2
        with:
          repository: bigler-webapps/workflow-templates
          ref: 74ee3545b96828aed8a29047aaab06a48d98d8f0  # v2.0.3

      - id: export
        uses: ./.github/actions/restore-source-export
```
and, in the job that ALSO needs a second repo's checkout without collision:
```yaml
      - name: Checkout workflow-templates (for composite actions)
        uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683  # v4.2.2
        with:
          repository: bigler-webapps/workflow-templates
          ref: 74ee3545b96828aed8a29047aaab06a48d98d8f0  # v2.0.3

      - name: Checkout webapp-ops-scripts
        uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683  # v4.2.2
        with:
          repository: bigler-webapps/webapp-ops-scripts
          ref: ${{ inputs.ops_scripts_ref }}
          path: ops-scripts

      - uses: ./.github/actions/restore-dest-import
```
Note that `source_export`'s job checks out `workflow-templates` to the workspace ROOT with no
`path:` — safe there ONLY because that job never needs the caller repo's own files. `app-ci.yml`'s
job is the opposite: it already needs the caller's checkout at the root (for the Dockerfile, build
context, `backend/requirements.txt`, etc. — see the "Build backend image" step at line 121). So
`app-ci.yml` must use the **`dest_import`-style** pattern: checkout `workflow-templates` into a
**named subfolder** (`path: ...`), leaving the caller's own checkout at the root untouched.

**The fix — insert a new step immediately before line 179's "Publish backend image to GHCR", and
change that step's `uses:`:**
```yaml
      - name: Checkout workflow-templates (for composite actions)
        uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683  # v4.2.2
        with:
          repository: bigler-webapps/workflow-templates
          ref: 1efa2e0d985b5d9e75e95c3a79c500a27fa5bcdb  # v2.9.0 — bump deliberately when a composite here changes
          path: .wt-checkout

      - name: Publish backend image to GHCR
        id: publish_backend_image
        uses: ./.wt-checkout/.github/actions/publish-backend-image
        with:
          image_tag: ${{ steps.resolve_sha.outputs.sha }}
          github_token: ${{ secrets.GITHUB_TOKEN }}
          backend_dockerfile: ${{ inputs.dockerfile }}
          backend_build_context: ${{ inputs.build-context }}
          backend_target: ${{ inputs.backend-target }}
          hram_engine_read_token: ${{ secrets.HRAM_ENGINE_READ_TOKEN }}
          vite_app_mui_license_key: ${{ secrets.VITE_APP_MUI_LICENSE_KEY }}
          existing_image: ${{ inputs.backend-target == '' && env.CI_IMAGE || '' }}
```
Keep every `with:` value under "Publish backend image to GHCR" UNCHANGED — `backend_dockerfile`
and `backend_build_context` are still relative to the caller repo's root (`GITHUB_WORKSPACE`, which
`.wt-checkout` sits inside but does not shadow), so the composite's own build step still resolves
the real app's Dockerfile correctly.

**Investigate and resolve the "Docker build-context pollution" risk named in Part A** before calling
this done: check whether the composite's internal `docker build` (triggered only for
`backend_target != ''` callers rebuilding the full image) sends `.wt-checkout` as part of its build
context, and whether that causes a real problem (build failure, meaningfully larger context) as
opposed to being cosmetically harmless. If it IS a real problem, the fix is a `.dockerignore`-scoped
exclusion or renaming the checkout path to one already covered by common `.dockerignore` patterns —
do not skip this check silently.

**Invariants / do-not-touch:**
- Do not change the checkout at line 112 (the caller's own checkout) — it must stay at the
  workspace root exactly as-is; other steps (build, pytest) depend on it.
- Do not change `resolve_sha` (line 114-116) — it must keep resolving the CALLER's checked-out SHA,
  not `workflow-templates`'s.
- The two other `uses: actions/checkout@...` occurrences in this file (lines 214, 272) belong to
  OTHER jobs in the same file — inspect whether they have the same bug (a local `./.github/actions/...`
  reference after a caller-repo checkout) before assuming line 185 is the only occurrence in the
  whole file; the Orchestrator's own survey found only one `uses: ./.github/actions/...` in this
  file (line 185), but re-verify against the landed file, since line numbers may have shifted.
