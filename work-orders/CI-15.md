# CI-15 — Fail CI on a duplicate i18n key, because JSON.parse never will

**Target repo:** `workflow-templates` (branch `main`)
**Tier:** 3 — CI/CD, and `app-ci.yml` is consumed by thirteen app repos pinned at `@main`, so this
lands everywhere the moment it merges.

**No prototype.** No surface.

**Precondition:** `innoservice`'s existing duplicates cleaned first (see *Ordering*). Landing this
before that turns a live app's CI red on merge.

---

## A. Envelope

### Goal & expected outcome

**Goal.** A duplicate key in an app's flat i18n translations file fails CI with a message naming the
key and both values.

**Expected outcome.** The failure mode that produced this order cannot recur silently.

### Why this exists

`JSON.parse` keeps the **last** occurrence of a duplicated key and reports nothing. In `jg-ferien`,
`OrganizationPage.TEAM_ROLE` was defined twice — the correct `Rolle` early in the file, a wrong
`Team` later — and the wrong one silently won in the running app. It was found by chance while
reading the file for an unrelated change (PUB-9), not by any check.

A sweep of the estate afterwards measured the rest: **twelve apps scanned, eleven clean.**
`innoservice` has five duplicated keys, four of them harmless (identical values) and one live:

```
Common.ConfirmDelete   1. en='Do you really want to delete?'  fr='Voulez-vous vraiment supprimer ?'
                       2. en='Really delete?'                 fr='Vraiment supprimer ?'   <-- wins
```

So the class is real, it is currently costing one app its intended English and French wording, and
nothing in the pipeline would ever have said so. `jg-ferien` alone carries 2067 keys and was edited
by two sessions in parallel on the day this was found.

### Scope

A step in `app-ci.yml`'s **`frontend` job** — it is a lint, and it belongs next to the lint.

- **Find the translations file by glob under `inputs.frontend-path`.** Two layouts exist in the
  estate: `<frontend-path>/i18n/translations.json` (jg-ferien) and
  `<frontend-path>/src/i18n/translations.json` (innoservice). Assuming one path silently checks
  nothing in half the estate — which is the same failure shape this order exists to prevent.
- **Blocking, not report-only.** The neighbouring `pnpm audit` and `pip-audit` steps are
  non-blocking because they are noisy and externally driven. This check is deterministic, has no
  false positives once scoped correctly, and the fix is deleting a line. It should fail the build.
- **The failure message is most of the value**: name the key, the number of occurrences, and each
  value, so the fix needs no investigation.
- **An app with no translations file passes.** Several repos have none or a stub; a missing file is
  not a failure.
- **Testable in this repo**, following the `.github/scripts/test_*.py` convention CI-14 established.
  A check that only ever runs in someone else's CI cannot be regression-tested here.

### The trap that must be tested, not assumed

Only **top-level** keys may be compared. The nested language keys (`de`, `en`, `fr`) repeat
legitimately inside every single entry — a naive duplicate scan flags all 2067 of them and the check
is worthless. The distinguishing property in this file format is that top-level keys contain a dot
(`Section.KEY`). Whatever rule the implementation uses, **the false-positive case belongs in the
tests**, because getting it wrong turns thirteen repos' CI red at once.

### Non-goals / do not touch

- **No other lint rules.** Not missing translations, not unused keys, not language-coverage parity —
  each is a defensible check and none of them is this one. They can follow separately if wanted.
- **No change to the `security` job**, its blocking/non-blocking split, or the audit steps.
- **No change to `pnpm lint` or `pnpm test`** or their input toggles.
- **No new required input on the reusable workflow.** Thirteen callers would each need editing, and
  the glob removes the need.
- **Do not fix any app's duplicates from here.** This order ships the check; the one known offender
  is handled separately (below).

### Ordering

`innoservice` is on `app-ci.yml@main` like everyone else, and it has five duplicates today. Merging
this check first would fail its CI on the next push, for a defect it did not introduce that day.
Clean `innoservice` first (Tier 1, `I18N-1` in that repo's register), then merge this.

### Risks

- **`@main` means no staged rollout.** All thirteen callers pick this up on merge, with no version to
  hold back on. A false positive is therefore not one broken build but thirteen. This is the reason
  the false-positive case is a required test rather than a nicety.
- **Runner assumptions.** The step must work with what the `frontend` job already has. Node's own
  `JSON.parse` cannot detect duplicates at all — a duplicate-aware parse is required, whatever the
  language.
- **A check nobody can read is a check nobody fixes.** If the failure says only "duplicate key
  found", the next person greps 2067 lines by hand.

### Required tests to WRITE

In this repo, alongside the existing `.github/scripts/test_*.py`:

- A fixture with a duplicated top-level key **fails**, and the message contains the key name and both
  values.
- A fixture with the normal repeated nested language keys and **no** duplicated top-level key
  **passes** — the false-positive guard, and the most important test here.
- A fixture with a key duplicated three times reports all three.
- A frontend path with no translations file **passes**.
- Both directory layouts (`i18n/` and `src/i18n/`) are found.
