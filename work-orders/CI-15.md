# CI-15 — Fail CI on a duplicate i18n key, because JSON.parse never will

**Target repo:** `workflow-templates` (branch `main`)
**Tier:** 3 — CI/CD, and `app-ci.yml` is consumed by thirteen app repos pinned at `@main`, so this
lands everywhere the moment it merges.

**No prototype.** No surface.

**Precondition:** `innoservice`'s existing duplicates cleaned first (see *Ordering*). Landing this
before that turns a live app's CI red on merge.

---

## A. Envelope

### Goal & expected outcome

**Goal.** A duplicate key in an app's flat i18n translations file fails CI with a message naming the
key and both values.

**Expected outcome.** The failure mode that produced this order cannot recur silently.

### Why this exists

`JSON.parse` keeps the **last** occurrence of a duplicated key and reports nothing. In `jg-ferien`,
`OrganizationPage.TEAM_ROLE` was defined twice — the correct `Rolle` early in the file, a wrong
`Team` later — and the wrong one silently won in the running app. It was found by chance while
reading the file for an unrelated change (PUB-9), not by any check.

A sweep of the estate afterwards measured the rest: **twelve apps scanned, eleven clean.**
`innoservice` has five duplicated keys, four of them harmless (identical values) and one live:

```
Common.ConfirmDelete   1. en='Do you really want to delete?'  fr='Voulez-vous vraiment supprimer ?'
                       2. en='Really delete?'                 fr='Vraiment supprimer ?'   <-- wins
```

So the class is real, it is currently costing one app its intended English and French wording, and
nothing in the pipeline would ever have said so. `jg-ferien` alone carries 2067 keys and was edited
by two sessions in parallel on the day this was found.

**JSON is the only unguarded format, which is why the check is scoped to it and not widened.**
ESLint's `no-dupe-keys` already catches a duplicated key in a JS object literal, and TypeScript
rejects one outright — so `ui-core-micha`'s `src/i18n/*Translations.ts` modules, whose keys reach all
thirteen apps and would therefore have the widest blast radius of any duplicate in the estate, are
covered by tools already in the pipeline. Nothing in it parses JSON for duplicates.

### Scope

A step in `app-ci.yml`'s **`frontend` job** — it is a lint, and it belongs next to the lint.

- **Find the translations file by glob under `inputs.frontend-path`.** Two layouts exist in the
  estate: `<frontend-path>/i18n/translations.json` (jg-ferien) and
  `<frontend-path>/src/i18n/translations.json` (innoservice). Assuming one path silently checks
  nothing in half the estate — which is the same failure shape this order exists to prevent.
- **Blocking, not report-only.** The neighbouring `pnpm audit` and `pip-audit` steps are
  non-blocking because they are noisy and externally driven. This check is deterministic, has no
  false positives once scoped correctly, and the fix is deleting a line. It should fail the build.
- **The failure message is most of the value**: name the key, the number of occurrences, and each
  value, so the fix needs no investigation.
- **An app with no translations file passes.** Several repos have none or a stub; a missing file is
  not a failure.
- **Testable in this repo**, following the `.github/scripts/test_*.py` convention CI-14 established.
  A check that only ever runs in someone else's CI cannot be regression-tested here.

### Detect per object, not across a flattened namespace

**A duplicate-aware parse reports duplicates within one object.** The nested language keys (`de`,
`en`, `fr`) repeat across *different* entry objects and never inside the same one, so per-object
detection has no false-positive case to guard against. Measured against both real files, with no
key-name heuristic of any kind:

```
jg-ferien/frontend/i18n/translations.json       -> 0 duplicates
innoservice/frontend/src/i18n/translations.json -> 6 duplicate occurrences
```

**Do not flatten the keys into one namespace first.** Flattening is the only thing that turns those
2067 repeated language keys into false positives, and the usual repair for it is a heuristic —
"top-level keys contain a dot (`Section.KEY`)" — resting on two conventions nothing enforces: that
every section key contains a dot (true today, 0 of 2067 without) and that no nested key ever does (a
locale tag such as `de-CH` would). Per Risk 1 a false positive is thirteen red builds, so an
implementation in which the case cannot arise is worth more than a rule that makes it unlikely.

The false-positive test below stays **required** — not as a guard against a live hazard, but to pin
the behaviour so a later rewrite cannot quietly reintroduce the flattening.

### Non-goals / do not touch

- **No other lint rules.** Not missing translations, not unused keys, not language-coverage parity —
  each is a defensible check and none of them is this one. They can follow separately if wanted.
- **No change to the `security` job**, its blocking/non-blocking split, or the audit steps.
- **No change to `pnpm lint` or `pnpm test`** or their input toggles.
- **No new required input on the reusable workflow.** Thirteen callers would each need editing, and
  the glob removes the need.
- **Do not fix any app's duplicates from here.** This order ships the check; the one known offender
  is handled separately (below).

### Ordering

`innoservice` is on `app-ci.yml@main` like everyone else, and it has five duplicates today. Merging
this check first would fail its CI on the next push, for a defect it did not introduce that day.
Clean `innoservice` first (Tier 1, `I18N-1` in that repo's register), then merge this.

### Risks

- **`@main` means no staged rollout.** All thirteen callers pick this up on merge, with no version to
  hold back on. A false positive is therefore not one broken build but thirteen. That is why the
  detection must be per-object rather than heuristic (above) — the point is an implementation in which
  the failure cannot occur, with the test pinning it rather than being the only thing standing in the
  way.
- **Runner assumptions.** The step must work with what the `frontend` job already has. Node's own
  `JSON.parse` cannot detect duplicates at all — a duplicate-aware parse is required, whatever the
  language.
- **A check nobody can read is a check nobody fixes.** If the failure says only "duplicate key
  found", the next person greps 2067 lines by hand.

### Required tests to WRITE

In this repo, alongside the existing `.github/scripts/test_*.py`:

- A fixture with a duplicated top-level key **fails**, and the message contains the key name and both
  values.
- A fixture with the normal repeated nested language keys and **no** duplicated section key **passes**
  — the regression pin for per-object detection, so a later rewrite cannot reintroduce flattening.
- A fixture with a key duplicated three times reports all three. Not hypothetical: `innoservice`'s
  `Common.Delete` is exactly this case, which is why the file yields six duplicate occurrences across
  five distinct keys.
- A frontend path with no translations file **passes**.
- Both directory layouts (`i18n/` and `src/i18n/`) are found.

  JSON with `json.dumps` (a Python dict can't hold a duplicate key; write the fixture as a raw
  string).
- Edit `workflow-templates/.github/workflows/app-ci.yml` — add a new step in the **`frontend` job**
  (starts at line 279), immediately after the existing **`Lint`** step (lines 298–301), before
  `Test` (line 303). New step shape:
  ```yaml
      - name: Check for duplicate i18n keys
        working-directory: ${{ inputs.frontend-path }}
        run: python3 ../.github/scripts/check_i18n_duplicate_keys.py .
  ```
  (adjust the relative path/args to whatever the script's CLI actually takes — the point is: runs in
  the `frontend` job, after `Lint`, unconditional — no `if:` toggle, per the Envelope's "blocking, not
  report-only" and "no new required input" non-goals). The script receives the frontend root (or is
  invoked from repo root with `inputs.frontend-path` — implementer's call, whichever keeps the glob
  logic simplest) and globs BOTH known layouts:
  `<frontend-path>/i18n/translations.json` and `<frontend-path>/src/i18n/translations.json`.

**Detection algorithm (the load-bearing part — read the Envelope's "Detect per object" section
above again before writing this):** parse the JSON with a duplicate-aware object hook
(`json.load(..., object_pairs_hook=...)` in Python — a hook receives the list of `(key, value)` pairs
for ONE JSON object at a time, at whatever nesting depth; count key occurrences within that single
call, not across the whole file). Do **not** flatten keys into one namespace first — the Envelope
explains exactly why that produces false positives on the repeated `de`/`en`/`fr` nested keys. A
duplicate found inside the top-level object (the one holding `"Common.Delete": {...}`) is a real
finding; a "duplicate" `de`/`en`/`fr` key only ever occurs inside *different* per-entry objects, so
per-object detection naturally never flags it — this is not a heuristic to get right, it's a
structural property of parsing one object at a time.

**Failure message:** for each duplicated key, print the key name, the occurrence count, and every
value (the full `{de, en, fr}` object) seen for it. Exit non-zero if any duplicate was found in any
scanned file; exit 0 (with a short "no translations file found, skipping" note) if a repo has neither
layout.

**Invariants / do-not-touch:** do not touch the `security` job, `pnpm lint`/`pnpm test` steps or their
`run-frontend-lint`/`run-frontend-tests` inputs, or add any new `workflow_call` input — the glob
already avoids needing one. Do not fix `innoservice`'s duplicates from this repo (that landed
separately as `innoservice` `I18N-1`, already merged to `develop` — confirmed clean via a per-object
duplicate check run directly against that file before this WO was dispatched).
